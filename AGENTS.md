# Project Engineering Rules

These rules govern all engineering work, architectural decisions, and agent contributions in this repository.

## Technical Foundation & Targets

- **Native Rust**: This is a native Rust project unless an approved design establishes a materially better alternative.
- **First-Class Platforms**: Windows and Linux are both first-class target operating systems. All code, terminal handling, and file paths must function identically and correctly on both.
- **Resource Discipline**: Runtime resource consumption (startup latency, memory footprint, CPU utilization, binary size) is a core product feature, not an afterthought.

## Runtime & Architectural Constraints

- **No Electron / Embedded Browsers**: No Electron, no Chromium Embedded Framework, no webviews, and no web frontends for the game.
- **No Heavy Runtime Dependencies**: No Node.js runtime requirement. No Python runtime requirement. No Java runtime requirement.
- **No Background Daemons**: No permanent background daemon unless later empirical evidence proves one is strictly necessary.
- **No Audio Dependency in V1**: No sound system or audio library dependencies in V1.
- **No Cloud or Network Requirements**:
  - No telemetry.
  - No analytics.
  - No advertising.
  - No network requirement for normal gameplay.
  - No account requirement.
  - No cloud saves in V1.
- **YAGNI & Lean Abstractions**: Do not introduce an abstraction solely because it might be useful one day. Every dependency and abstraction requires concrete justification.

## Code Quality & Engineering Hygiene

- **No Dead or Commented-Out Code**: No dead code. No commented-out obsolete code. Delete obsolete implementation instead of leaving historical code commented out.
- **No Unused Dependencies**: Keep dependency trees audited and strictly lean.
- **No Placeholders Represented as Complete**: No stubbed or fake implementations claiming completion.
- **No Fake Tests**: Tests must execute real logic, assert actual behavior, and verify failure modes.
- **Evidence-Based Metrics**:
  - No benchmark numbers that were not actually measured.
  - No "blazing fast", "zero overhead", "production ready", or similar marketing claims without empirical evidence.
  - Every significant completion claim requires concrete verification evidence.

## Authorship, Style & Documentation Standards

- **Professional Authorship**: Do not add "generated by AI", AI attribution, AI badges, or agent chatter to source files, documentation, commits, or repository metadata.
- **Idiomatic Rust**: Use idiomatic Rust naming conventions and standard project layout.
- **Format with rustfmt**: Let `rustfmt` format Rust code. Do not invent arbitrary style rules that fight the Rust ecosystem.
- **Markdown Formatting**: Markdown prose must not be hard-wrapped at 80 columns merely for style.
- **Domain-Driven Organization**: File and module names must describe real domain concepts. No strange generated folder structures, and no unnecessary architecture layers.
- **Professional Documentation**: Documentation must read like professional developer documentation, not an automated report.
- **Comments**: Comments explain non-obvious reasoning, invariants, and edge cases, not obvious syntax.
- **Document Architectural Decisions**: Document important architectural decisions briefly in `docs/decisions/` when future maintainers would otherwise repeat the investigation.

## Security & Transparency

- **No Committed Secrets**: API tokens, credentials, and private keys must never be committed.
- **No Security Through Obscurity**: Do not intentionally obfuscate the architecture to prevent other developers or coding agents from understanding it. Security and save integrity must come from sound design, not obscurity.
